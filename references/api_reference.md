# Довідка: Wikimedia API, які використовує ця навичка

Читай цей файл, коли потрібно зрозуміти, чому щось повернуло помилку,
або коли треба скласти запит вручну (у обхід скриптів) — наприклад,
для нетипового ендпоінту, якого немає в scripts/.

## 1. Pageviews REST API (`fetch_pageviews.py`, `wm_api.pageviews_per_article`)

```
GET https://wikimedia.org/api/rest_v1/metrics/pageviews/per-article/
    {project}/{access}/{agent}/{article}/{granularity}/{start}/{end}
```

- `project` — `<lang>.wikipedia`, напр. `pl.wikipedia`, `uk.wikipedia`.
- `access` — `all-access` (за замовчуванням) / `desktop` / `mobile-app` / `mobile-web`.
- `agent` — **завжди використовуй `user`**, якщо мета — людський інтерес.
  `all-agents` включає ботів і краулерів, які можуть спотворити картину
  (особливо для нішевих статей з малим людським трафіком).
- `article` — точна назва сторінки, пробіли → `_`, потім URL-encode.
  Неправильна назва не дає помилки типу "стаття не знайдена" — просто
  повертає 404 або (гірше) дані про геть іншу статтю, якщо назва випадково
  збіглась з редиректом. **Завжди резолвити назву через `resolve_article.py`
  перед запитом**, не вгадувати переклад самостійно.
- `granularity` — `daily` або `monthly`. Для періодів довше ~6 місяців
  зазвичай достатньо `monthly` — це і швидше, і менш шумно.
- `start`/`end` — формат `YYYYMMDDHH` (година завжди `00`).

**Найважливіше обмеження**: дані per-article доступні лише з **липня 2015
року**. Запит на "останні 10 років" фізично не може повернути дані
раніше цього. `fetch_pageviews.py` автоматично обрізає початкову дату
і додає про це попередження (`warnings`) у вихідний JSON — завжди
перевіряй це поле і повідомляй користувачу, якщо його запитаний період
було обрізано.

Ліміт швидкості офіційно не документований жорстко, але етикет Wikimedia
вимагає: (1) власний `User-Agent` з контактом (заданий у `wm_api.py` —
за потреби зміни на реальний контакт проєкту), (2) не бомбардувати
паралельними запитами. Послідовні запити з невеликою затримкою (як у
скриптах) — прийнятна практика.

## 2. MediaWiki Action API — пошук статті (`resolve_article.py`)

```
GET https://{lang}.wikipedia.org/w/api.php
    ?action=query&list=search&srsearch={термін}&srlimit=1&format=json
```

Повертає найрелевантнішу статтю мовою `{lang}` за довільним пошуковим
запитом. Це "вхідна точка" резолюції: береться перший результат пошуку
мовою-підказкою (за замовчуванням англійська, бо там найбільш повний
граф зв'язків з Wikidata).

## 3. MediaWiki Action API — Wikidata QID сторінки

```
GET https://{lang}.wikipedia.org/w/api.php
    ?action=query&prop=pageprops&titles={назва}&ppprop=wikibase_item&format=json
```

Дає `Q-ідентифікатор` (QID) статті у Wikidata — ключ до крос-мовного
пошуку відповідників.

## 4. Wikidata Action API — sitelinks

```
GET https://www.wikidata.org/w/api.php
    ?action=wbgetentities&ids={QID}&props=sitelinks&format=json
```

Повертає точні назви статті **усіма мовними Вікіпедіями одразу** —
найнадійніший спосіб знайти відповідник, без множинних пошукових
запитів. `resolve_article.py` йде цим шляхом, а прямий пошук
(`list=search`) використовує лише як fallback, якщо мови немає серед
sitelinks (стаття може існувати без зв'язку у Wikidata).

## Типові помилки та як їх читати

| Симптом | Ймовірна причина |
|---|---|
| 404 на pageviews | Неправильна/незбігова назва статті, або стаття не існувала в запитаний період |
| Порожній масив `points`, але без помилки | Стаття існує, але мала 0 переглядів кожен день/місяць (малоймовірно, але буває для дуже нішевих тем) — або невірний `project` (напр. переплутано `wikipedia`/`wikivoyage`) |
| `_not_found` у виводі `resolve_article.py` | Немає ні sitelink, ні результатів пошуку — тема, ймовірно, не має статті цією мовою взагалі. Це саме по собі є сигналом (немає навіть енциклопедичної статті — точно замало даних для оцінки продуктового попиту) |
| Різкий стрибок в один період | Дивись `outlier_periods` у виводі `trend_analysis.py` — це не обов'язково помилка даних, а може бути реальний вірусний спалах уваги (новина, подія) |
