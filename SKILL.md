# Wikipedia Trends — навичка для продуктових рішень на основі Wikipedia

## Що це і навіщо

Ця навичка допомагає відповідати на запитання на кшталт "чи зростає
інтерес до теми X", "де запускати продукт Y", "яку тему додати наступною"
— використовуючи перегляди статей Wikipedia як дешевий і швидкий (хоч і
недосконалий) проксі-сигнал інтересу аудиторії. Вона не просто малює
графік — вона рахує, **наскільки видимому тренду можна довіряти**, і
завжди чесно повідомляє про обмеження цього сигналу.

Прочитай `references/methodology.md`, якщо потрібно зрозуміти або
пояснити користувачу, *чому* висновок сформульовано саме так — там
детально описано логіку оцінки довіри до тренду. Прочитай
`references/api_reference.md`, якщо запит до API повернув помилку і
незрозуміло чому. `references/roadmap.md` — не для звичайних запитів, а
для випадків, коли користувач просить розвинути саму навичку далі.

## Швидкий шлях: один виклик на типовий запит

Для більшості запитів (одна тема, кілька мов, порівняння за період)
достатньо одного виклику оркестратора:

```bash
python scripts/wiki_trends.py \
  --topic "intermittent fasting" \
  --langs pl,cs \
  --years-back 2 \
  --title "Інтервальне голодування: PL vs CS" \
  --workdir /tmp/wt_fasting \
  --out /mnt/user-data/outputs/report.pdf
```

Це виконає резолюцію назв статей → завантаження даних → аналіз тренду →
збірку PDF. Постав `--workdir` на постійне (для цього запиту) місце —
проміжні файли там (`resolved.json`, `data.json`, `analysis.json`)
знадобляться для дешевих уточнюючих запитів (див. розділ нижче).

**Завжди перевіряй stderr-вивід оркестратора** на попередження — зокрема
"статтю не знайдено для мов: [...]" та обрізання періоду через ліміт
API (з липня 2015). Якщо щось із цього сталось, обов'язково згадай це у
відповіді користувачу, а не мовчки покажи звіт як повний.

## Коли розбивати на окремі кроки замість оркестратора

Використовуй `resolve_article.py`, `fetch_pageviews.py`,
`trend_analysis.py`, `build_report.py` окремо, коли:

- **Користувач сам знає точні назви статей** для порівняння (напр. хоче
  порівняти дві різні, але споріднені статті однією мовою — це не
  "одна тема різними мовами", а вручну вказаний список). У цьому
  випадку одразу йди в `fetch_pageviews.py --series lang:"Точна назва" ...`,
  пропускаючи резолюцію.
- **Потрібно уточнити або повторити частину аналізу** без повторного
  скачування даних — див. наступний розділ.
- **Порівняння тем, а не мов** (один і той самий мовний розділ, кілька
  різних статей) — `wiki_trends.py` заточений під "одна тема, кілька
  мов"; для "кілька тем, одна мова" зручніше зібрати `--series` вручну
  через `fetch_pageviews.py` (лейбли можуть бути назвами тем замість
  мовних кодів, наприклад `--series fasting:"Intermittent fasting" keto:"Ketogenic diet"`,
  просто вкажи однаковий `lang` префікс у власній інтерпретації —
  скрипт лише використовує label як ключ, а не обов'язково як мову).
- **Потрібен нестандартний звіт** (інший текст, додаткові розділи) —
  тоді бери `analysis.json` і формуй PDF власним кодом на основі
  `build_report.py` як прикладу, або став аналіз у відповідь просто
  текстом/таблицею в чаті, якщо PDF не потрібен.

## Ефективні уточнюючі запити (не роби все заново)

Користувачі часто уточнюють запит після першої відповіді ("а що як
взяти лише останній рік", "додай ще й словацьку", "а покажи в
абсолютних цифрах, а не в індексі"). Не перезапускай увесь пайплайн
з нуля, якщо не потрібно:

| Уточнення | Що саме перезапустити |
|---|---|
| Інший період (той самий набір мов/статей) | Лише `fetch_pageviews.py` з новими `--start/--end`, потім `trend_analysis.py` + `build_report.py` |
| Додати ще одну мову | `resolve_article.py` лише для нової мови → домалювати серію в `data.json` (або перезапустити `fetch_pageviews.py` з повним оновленим `--series`) → `trend_analysis.py` + `build_report.py` |
| Інший заголовок/текст звіту, ті самі дані | Лише `build_report.py` — `analysis.json` не змінюється |
| "Наскільки цьому можна довіряти?" | Дані вже в `analysis.json` (`confidence`, `confidence_reasons`, `r_squared`, `outlier_periods`) — просто поясни їх словами, мережевий виклик не потрібен |
| Зміна припущення (напр. "а якщо не відфільтровувати ботів") | Повторний `fetch_pageviews.py --agent all-agents` |

Тримай `--workdir` для сесії стабільним, щоб проміжні файли лишались
доступними для таких уточнень.

## Як інтерпретувати й подавати результат користувачу

Не обмежуйся тим, щоб віддати PDF і сказати "ось звіт". Користувач —
засновник продукту, а не аналітик даних. У текстовій відповіді:

1. Дай **пряму відповідь на бізнес-питання** одним-двома реченнями
   ("Інтерес до інтервального голодування зростає в обох мовах, але в
   польській — стійкіше і швидше").
2. Назви **рівень довіри** простою мовою, спираючись на
   `confidence`/`confidence_reasons` з `analysis.json` — не просто
   "high/medium/low", а чому саме (короткий ряд? шумні дані? сплеск,
   що міг спотворити картину?).
3. Явно розмежуй **відносне зростання** (хто росте швидше) і
   **абсолютний розмір аудиторії** (хто вже великий) — це різні речі,
   і засновники продуктів зазвичай хочуть знати обидві.
4. Заверши **пропозицією наступного кроку**, коли це доречно
   (напр. "варто перевірити ще раз через квартал", "вартувало б
   доповнити пошуковими трендами Google, бо Wikipedia — лише один
   сигнал", "перевір також суміжні статті — X, Y").
5. Якщо resolve_article.py не знайшов статтю для якоїсь мови — це
   само по собі сигнал (немає навіть енциклопедичної статті цією
   мовою), і про це варто сказати прямо, а не просто мовчки виключити
   мову зі звіту.

## Обмеження, про які треба пам'ятати завжди

- Дані Pageviews API існують лише з **липня 2015 року**.
- Wikipedia pageviews — сигнал **цікавості почитати про тему**, не
  готовності платити чи наміру купити. Це відправна точка для подальшої
  перевірки (напр. пошуковими трендами, опитуванням, пілотним запуском),
  а не самодостатній доказ попиту.
- Мова розділу ≈ мова читання, не країна чи національність аудиторії.
- Короткі ряди (менше року) і ряди з високою часткою різких сплесків
  ніколи не варто подавати як надійний тренд — про це подбає
  `confidence`, але словесна відповідь має це підсилити, а не
  згладжувати.

## Формат вихідних файлів (для власної розробки/розширення)

- `resolved.json` — `{lang: {title, resolved_via, qid}, "_not_found": [...]}`.
- `data.json` — `{series: {label: {title, project, points: [{date, views}], warnings}}}`.
- `analysis.json` — `{analyses: {label: {n_periods, monthly_growth_pct, total_change_pct, r_squared, coefficient_of_variation, outlier_periods, confidence, confidence_reasons, warnings, indexed_points, source_warnings, title}}, ranking: [label, ...]}`.
- `report.pdf` — односторінковий: заголовок, графік індексованих трендів, таблиця метрик, текстовий блок висновків і застережень.

Кожен скрипт читає/пише саме ці формати — тож будь-який крок пайплайну
можна замінити власним кодом, якщо він поважає ці контракти.
